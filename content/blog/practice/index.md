# HTTP 浏览器

# GET和POST区别

* **请求参数的位置**：GET请求参数一般在URL上拼接，是query参数。POST请求参数一般在请求体Body中。（GET请求参数规范不建议放在请求体中，经我实践GET请求参数放入请求体中会被chrome过滤掉。POST请求也可放一些简单的参数在URL上，但通常不会这样。）
* **请求长度的限制**：HTTP本身没有限制请求参数长度。但是一般浏览器会有URL长度2000字符的限制，所以GET请求是有参数长度限制的，服务器一般对URL长度限制更宽松。请求体Body参数大小一般无限制。
* **安全性**：GET请求的参数会暴露在URL中，且可能会被浏览器和代理服务器缓存等，POST一般在请求体Body传参，所以要比GET更安全。但是不是绝对安全的，只有开启https，可以将请求头、请求体、URL路径参数加密，安全传输。
* **幂等性**：GET请求是幂等的，即多次执行同一GET请求，服务器将返回相同的结果。而POST请求则不是幂等的，因为每次提交都会创建新的资源。（实际开发过程中GET请求api看服务器请求头设置是否缓存，一般静态资源默认缓存，动态查询数据不缓存）
* **缓存**：GET的幂等性，请求默认是缓存的，但是也可以在服务端响应头Cache-Control: no-store不缓存。POST请求默认不缓存，但是也可以在向银行头设置Cache-Control或Expires来进行缓存控制。

# https怎么保证安全的

* **加密传输**：HTTPS使用SSL/TLS协议对HTTP报文进行加密，使得敏感数据在网络传输过程中不容易被窃听和篡改。这种加密过程结合了对称加密和非对称加密，确保数据的保密性和完整性。
* **身份验证**：HTTPS通过数字证书进行身份验证，确保通信双方的真实性。在建立HTTPS连接时，服务器会提供数字证书来证明自己的身份。如果验证通过，客户端就可以信任服务器，并继续与其进行安全的数据传输。这有效防止了被恶意伪装的服务器攻击。
* **数据完整性保护**：在传输数据之前，HTTPS会对数据进行加密，并使用消息摘要（hash）算法生成一个摘要值。在数据到达接收端后，接收端会使用相同的算法对接收到的数据进行摘要计算，并与发送端的摘要值进行比较。如果两者一致，说明数据在传输过程中没有被篡改。如果不一致，通信双方应重新进行验证或中断连接。

HTTPS 提供了比 HTTP 更强的安全性和隐私保护，但在性能、成本、管理复杂性和兼容性方面有一定的缺点。尽管如此，随着技术的进步和 SSL/TLS 协议的优化，这些缺点在逐渐减少。如今，HTTPS 已成为互联网传输的标准，因此它的优点通常被认为远远超过其缺点。

# HTTP状态码

## 1xx（信息性状态码）

* 100 Continue：客户端应继续其请求。
* 101 Switching Protocols：表示服务器同意切换协议。（使用websocket时，会先发送一个http请求返回101，然后才会建立socket连接。这种设计确保了 WebSocket 可以与现有的 HTTP 基础设施无缝集成，并且在协议切换前具备一定的安全性和兼容性。）

## 2xx（成功状态码）

* 200 OK：请求成功。
* 201 Created：请求已经被实现，并因此创建了一个新的资源。
* 204 No Content：服务器成功处理了请求，但没有返回任何内容。

## 3xx（重定向状态码）

* 301 Moved Permanently：请求的资源已被永久移动到新的URL上。
* 302 Found：请求的资源现在临时从不同的URL响应请求。
* 304 Not Modified：客户端已经执行了GET请求，但文件未发生变化。（协商缓存常见）

## 4xx（客户端错误状态码）

* 400 Bad Request：服务器无法理解请求。
* 401 Unauthorized：请求要求进行身份验证。
* 403 Forbidden：服务器理解请求，但拒绝执行它。
* 404 Not Found：服务器无法找到请求的资源。
* 405 Method Not Allowed：请求中指定的方法不被允许。

## 5xx（服务器错误状态码）

* 500 Internal Server Error：服务器遇到了一个未曾预料的情况，导致其无法完成对请求的处理。
* 501 Not Implemented：服务器不支持当前请求所需要的某个功能。
* 503 Service Unavailable：由于临时的服务器维护或者过载，服务器当前无法处理请求。
# OPTION请求

##  跨域资源共享（CORS）预检请求

* CORS（Cross-Origin Resource Sharing） 是浏览器的一项安全机制，用于允许一个域名下的网页访问另一个域名下的资源。为了确保安全性，浏览器在发送实际请求前，可能会发送一个 OPTIONS 请求，称为 预检请求。
* 预检请求的目的是让服务器告知浏览器，是否允许该跨域请求，以及支持的 HTTP 方法和头部。

**实例**

```http

OPTIONS /api/data HTTP/1.1
Host: example.com
Origin: http://example.org
Access-Control-Request-Method: POST
Access-Control-Request-Headers: X-Custom-Header

```

```http

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://example.org
Access-Control-Allow-Methods: POST, GET, OPTIONS
Access-Control-Allow-Headers: X-Custom-Header

```

##  查看服务器支持的 HTTP 方法

* 使用 OPTIONS 方法可以查询服务器在特定资源上支持的所有 HTTP 方法。这在调试 API 时很有用，帮助开发者了解对特定资源可以执行哪些操作。

**实例**

```http

OPTIONS /api/users HTTP/1.1
Host: example.com

```

```http

HTTP/1.1 200 OK
Allow: GET, POST, PUT, DELETE, OPTIONS

```

## 服务器健康检查

* OPTIONS 请求也可以用于服务器健康检查，因为它不会改变服务器状态，通常也不会触发复杂的处理逻辑。因此，可以使用它快速检查服务器或特定资源是否可用。

##  API 调试和文档

* 在开发 API 时，OPTIONS 请求可以用于自动生成 API 文档或帮助文档工具，列出所有可用的操作和配置。

# HTTP的keep-alive

**HTTP的keep-alive，也称为HTTP长连接，是一种通过重用TCP连接来发送和接收多个HTTP请求的机制。**

## 优点

* 减少连接建立开销：在没有keep-alive的情况下，每次HTTP请求都需要经过TCP三次握手建立连接，这会导致较大的延迟和资源消耗。而使用keep-alive，可以在一个TCP连接上发送多个HTTP请求，从而减少了建立连接的开销。
* 降低网络负载：每次建立和关闭连接时，都会消耗网络带宽和服务器资源。通过保持持久连接，可以减少连接的频繁建立和关闭，从而降低了网络负载和服务器负载。
* 提高性能和响应时间：由于避免了连接建立和关闭的开销，keep-alive可以提高请求的响应时间和整体性能。客户端可以在同一个连接上连续发送请求，而服务器也可以在保持连接的情况下更快地响应这些请求。
* 支持HTTP管道化：HTTP管道化是允许客户端在同一TCP连接中连续发送多个请求而无需等待每个请求的响应的技术。当与keep-alive结合使用时，可以进一步提高性能。

## 缺点

* 难以做负载均衡
* 资源消耗更多
* 配置复杂性

## HTTP kepp-alive长连接相比websocket长连接

* 通信模型：
Keep-Alive：适用于传统的请求-响应模型，不适合实时双向通信。（半双工通信，通信是单向的，即客户端请求，服务器响应，无法实现实时的双向通信）
WebSocket：适用于实时双向通信，需要持续交换数据的场景。

* 复杂性：
Keep-Alive：实现简单，易于部署，兼容性好，但功能有限。
WebSocket：功能强大，但实现和管理复杂度更高。

* 资源消耗：
Keep-Alive 和 WebSocket 都需要维护连接，会消耗资源，但 WebSocket 在高并发和长时间连接的场景中，资源消耗可能更为显著。

* 使用场景：
Keep-Alive：适合浏览器与服务器之间的频繁但非实时的通信，如网页加载多个资源（图像、CSS、JS 文件等）。
WebSocket：适合需要实时数据交换的应用，如实时聊天、在线游戏、股票行情推送等。

HTTP Keep-Alive 和 WebSocket 都提供了保持连接的方法，但它们的适用场景和设计目标不同。Keep-Alive 主要用于减少 HTTP 请求的连接开销，适合传统的请求-响应模型；而 WebSocket 则用于实时双向通信，适合需要持续数据交换的应用。
两者的缺点主要集中在资源消耗、复杂性和安全性上。选择哪种方式，取决于具体的应用需求和场景。如果需要实时双向通信，WebSocket 是更好的选择；如果是传统的网页加载或 API 调用，Keep-Alive 可能已经足够了。

# 输入URL到看到页面发生的全过程
* URL 解析
浏览器首先解析输入的 URL，以确定协议（如 http 或 https）、主机名、端口号（如果有指定）以及路径、查询参数等。

* DNS 解析
浏览器需要将域名（如 www.example.com）转换为 IP 地址。为此，它会先检查本地缓存（DNS 缓存）或操作系统缓存。如果本地缓存中没有找到，浏览器会发起 DNS 请求到 DNS 服务器，DNS 服务器返回对应的 IP 地址。

*  建立 TCP 连接
获取到 IP 地址后，浏览器会与该 IP 地址的服务器建立 TCP 连接。
对于 HTTPS 协议，建立连接的过程包括：
三次握手：客户端与服务器进行三次握手以建立可靠的 TCP 连接。
TLS/SSL 握手（如果是 HTTPS）：建立安全的加密通信通道，客户端与服务器协商加密算法，并交换证书，验证服务器身份。

* 发送 HTTP 请求
TCP 连接建立后，浏览器会构建 HTTP 请求并发送给服务器。这个请求包括：
请求行：如 GET /path HTTP/1.1
请求头：包括 Host、User-Agent、Accept、Cookie 等信息。
请求体（POST 请求才有）：包含要发送给服务器的数据。

* 服务器处理请求
服务器接收到请求后，根据请求的 URL 路径和其他参数，决定如何处理。服务器可能：
返回静态文件（如 HTML、CSS、JS 文件）。
执行服务器端代码（如 PHP、Node.js）生成动态内容。
查询数据库获取数据并返回。
服务器处理完请求后，会返回 HTTP 响应，包括：
状态码：如 200 OK，404 Not Found。
响应头：如 Content-Type、Cache-Control 等。
响应体：即 HTML 文档、JSON 数据、图片等实际内容。

* 浏览器接收响应
浏览器接收到服务器的 HTTP 响应后，会首先检查状态码，确认请求是否成功。
然后根据响应头的信息，决定如何处理响应体的内容。

* 解析 HTML 文档
浏览器开始解析 HTML 文档，构建 DOM 树（Document Object Model）。
遇到 CSS 文件、JavaScript 文件、图片等资源时，浏览器会发起新的 HTTP 请求来获取这些资源。

* 构建 CSSOM 树
在获取到 CSS 文件后，浏览器会解析 CSS，并与 DOM 树合并，生成渲染树（Render Tree）。
渲染树包含了每个节点的视觉信息，如颜色、尺寸、位置等。

* 执行 JavaScript
浏览器会解析并执行 JavaScript 文件。JavaScript 可以操作 DOM 树和 CSSOM 树，动态地改变页面内容。
如果 JavaScript 文件使用了 async 或 defer，则可能会影响执行的顺序，async 的脚本会在获取到后立即执行，而 defer 的脚本会在页面解析完成后再执行。

* 布局（Layout）和绘制（Painting）
根据渲染树，浏览器计算每个元素在屏幕上的位置和大小，这个过程叫做 布局（Layout）。
然后，浏览器会将页面元素绘制到屏幕上，这个过程叫做 绘制（Painting）。

* 显示页面
页面元素被绘制到屏幕后，你就可以看到最终呈现的页面了。
随着页面的继续加载，可能会有更多的资源被获取和执行（如图片、动态数据等），页面可能还会进一步更新。

# 浏览器缓存的优先级
* Service Worker 缓存：由于其可以完全控制网络请求，因此具有最高的优先级，即使是强制缓存也可以被它所覆盖。Service Worker是运行在浏览器背后的独立线程，一般可以用来实现缓存功能。但请注意，由于Service Worker中涉及到请求拦截，所以必须使用HTTPS协议来保障安全。

* Memory Cache（内存缓存） ：这是内存中的缓存，主要包含的是当前页面中已经抓取到的资源，如样式、脚本、图片等。当我们访问过页面以后，再次刷新页面，可以发现很多数据都来自于内存缓存。

* HTTP Cache（HTTP缓存）：这包括强制缓存和协商缓存。

强制缓存：在有效时间内，不会向服务器发送请求，直接从缓存中读取资源。控制强制缓存的字段分别是Expires和Cache-Control，其中Cache-Control的优先级高于Expires。
协商缓存：当强制缓存失效后，浏览器会携带缓存标识向服务器发起请求，由服务器根据缓存标识决定是否使用缓存。控制协商缓存的字段有Last-Modified/If-Modified-Since和Etag/If-None-Match。

* Disk Cache（磁盘缓存） ：存储在硬盘中的缓存，读取速度较慢，但胜在容量和存储时效性上。

* Push Cache（推送缓存） ：这是HTTP/2中的内容，当以上四种缓存都没有命中时，它才会被使用。

# 跨域和常用解决方法

## 同源策略

跨域问题的存在主要是因为浏览器的同源策略限制。同源策略是浏览器的一种安全机制，旨在防止一个域的脚本与另一个域的内容进行交互，以保护用户免受诸如跨站脚本攻击（XSS）和跨站请求伪造（CSRF）等安全威胁。所谓同源，指的是两个页面具有相同的协议（如http或https）、主机（域名或IP地址）和端口号。当这三个条件中任何一个不匹配时，就会触发跨域问题。

## 跨域解决

* JSONP：利用script标签不受同源策略限制的特性，通过动态插入标签来请求不同源的数据。JSONP只支持GET请求，并且需要在服务器端进行相应的配合。
* CORS（跨域资源共享） ：CORS 是一种 W3C 规范，它定义了一种浏览器和服务器交互的方式来确定是否允许跨源请求。通过服务器端设置相应的HTTP头部信息，如Access-Control-Allow-Origin，来允许跨域请求。CORS 支持各种HTTP请求方法，并且更加灵活和安全。
* 代理服务器：通过搭建一个代理服务器来转发请求，使得前端可以通过代理服务器来间接访问不同源的资源。这样，前端请求实际上是发往同源的代理服务器，再由代理服务器去请求不同源的资源。

正向代理：代理客户端，帮助客户端访问服务器。通常用于控制客户端的访问权限、隐藏客户端身份和突破网络限制。（前后端开发过程中，webpack配置的代理）
反向代理：代理服务器，帮助服务器处理来自客户端的请求。通常用于负载均衡、安全防护、隐藏服务器身份等。（部署ngix反向代理）

# 浏览器的渲染机制

## 机制

* 解析 HTML 生成 DOM 树
* 解析 CSS 生成 CSSOM 树
* 生成 Render 树
Render 树构建：浏览器将 DOM 树和 CSSOM 树结合，生成 Render 树（渲染树）。Render 树包含了每个可见元素的视觉信息，如尺寸、位置、颜色等。
不可见元素排除：在 Render 树中，不可见的元素（如 display: none）不会被包含。
* 布局（Layout）
布局计算：浏览器根据 Render 树中元素的几何信息，计算每个元素在屏幕上的确切位置和尺寸，这个过程称为布局或回流（Reflow）。
从上到下：布局通常是从根元素（<html>）开始，逐步计算子元素的位置和尺寸。
* 绘制（Painting）
绘制过程：在布局完成后，浏览器会根据 Render 树的内容，绘制每个节点的视觉表现（如背景颜色、文本、边框、阴影等）到多个绘制层（Paint Layers）。
绘制层：不同的元素可能会被绘制到不同的图层中，这样可以优化渲染效率。
* 合成与显示（Compositing）
合成图层：浏览器将各个绘制层合成一个图像，这个过程称为合成（Compositing）。浏览器 GPU 可能会参与加速这个过程。
显示页面：合成后的图像最终会被绘制到屏幕上，用户可以看到完整的页面内容。
* JavaScript 执行与重绘
JavaScript 执行：如果页面包含 JavaScript，浏览器会在解析和渲染过程中执行脚本。JavaScript 可以修改 DOM 和 CSSOM，这会触发重排（Reflow）或重绘（Repaint）。
重排（Reflow）：如果 JavaScript 改变了元素的布局信息（如大小、位置），浏览器会重新计算布局，这称为重排。
重绘（Repaint）：如果 JavaScript 只改变了元素的视觉样式（如颜色、背景），浏览器会触发重绘，不会涉及布局计算。
* 渲染优化
避免阻塞渲染：某些资源（如 JavaScript 文件）可能会阻塞页面的解析和渲染，现代浏览器会采取异步加载、延迟执行等方式来优化渲染速度。
层次优化：通过合理使用 CSS 样式（如 will-change、transform），开发者可以提示浏览器对某些元素进行图层分离，从而加速渲染。

## 渲染机制中的关键点

* 主线程和渲染线程：渲染过程中的大部分工作（如 DOM 解析、布局计算、绘制等）发生在浏览器的主线程中，这意味着 JavaScript 执行可能会阻塞渲染。
* 异步加载：通过 async 和 defer 属性，可以让脚本异步加载，避免阻塞渲染。
* 回流与重绘：频繁触发回流和重绘会降低页面性能，优化代码以减少不必要的 DOM 操作是关键。

# 回流（重排）和重绘

## 回流 Reflow

回流（或称为“重排”）是指当页面的布局或几何属性（如宽度、高度、位置、边距等）发生变化时，浏览器需要重新计算元素的位置和尺寸，并重新构建渲染树。回流是一个代价昂贵的操作，因为它可能导致部分或整个页面的重新布局。

**触发情况**

* 添加或删除可见的 DOM 元素。
* 元素的尺寸、位置、显示状态变化（如 width、height、margin、padding 等）。
* 浏览器窗口尺寸变化导致页面布局变化。
* 内容的改变（如输入框内容改变）。
* 获取某些属性（如 offsetHeight、clientWidth）时，由于需要准确的值，浏览器可能会强制回流。

## 重绘 Repaint

重绘是指当元素的外观样式（如颜色、背景、阴影等）发生变化时，但不影响元素的布局时，浏览器只需要重新绘制这些元素的样式，不需要重新计算布局。相比回流，重绘的代价较低，但如果频繁触发，也会影响性能。

**触发情况**

* 改变元素的视觉属性（如 color、background-color、visibility 等）。
* 修改 transform、opacity 等不会影响布局的样式属性。

## 减少回流和重绘的优化方法

* 批量操作 DOM
减少 DOM 操作次数：如果需要对多个元素进行操作，可以通过批量操作或将操作放入文档片段中，然后一次性插入 DOM 中。例如，可以使用 document.createDocumentFragment() 来减少多次 DOM 插入操作带来的回流。
使用 display: none：在进行复杂的 DOM 操作时，可以先将元素的 display 设置为 none，操作完成后再恢复，这样可以减少多次回流。

* 缓存布局信息
避免频繁读取布局信息：避免频繁读取会导致回流的属性（如 offsetHeight、offsetWidth），如果需要多次使用，可以将它们缓存起来，避免重复计算。
避免触发同步布局：在读取某些属性（如 offsetHeight）后立即修改布局，会强制浏览器同步计算布局，从而触发回流，应该尽量避免这种操作。

* 使用 transform 和 opacity
减少对布局属性的修改：如果只需要移动或调整元素的外观，尽量使用 CSS3 的 transform 或 opacity，这些属性通常不会触发回流，只会触发重绘。

* 使用合适的 CSS
避免使用复杂的 CSS 选择器：使用简单且高效的选择器，避免影响到较大的 DOM 树范围。
避免使用 table 布局：表格布局会导致大量的回流，因为当表格中的任何一个元素变化时，整个表格都会重新计算布局。

* 减少样式的层叠影响
样式层叠和级联：CSS 样式的层叠和级联会影响回流的范围。尽量减少全局样式的复杂度，保持样式的简单明了。

## 总结

* **回流（Reflow）：涉及布局变化，需要重新计算元素的位置和尺寸，是一个代价昂贵的操作。**
* **重绘（Repaint）：涉及元素外观样式变化，只需要重新绘制，不涉及布局计算。**

# 浏览器事件机制

浏览器的事件机制主要涉及到事件的触发、传播和处理。当用户在浏览器中进行某些操作，如点击按钮、移动鼠标或输入文本时，会触发相应的事件。这些事件被封装为event对象，包含了事件的属性和方法，供开发者在事件处理函数中使用。

事件的传播过程分为三个阶段：捕获阶段、目标阶段和冒泡阶段。在DOM2级事件模型中，事件首先在最外层HTML元素上开始捕获，然后向下传递到事件的目标元素，沿途触发所有设置了捕获事件处理器的元素。接着，事件处理器在事件的目标元素上执行，这是事件处理的核心阶段。最后，事件从目标元素向上回溯，触发所有设置了冒泡事件处理器的元素，完成冒泡阶段。这种机制允许开发者在事件传播的不同阶段拦截并处理事件。

常见的事件类型包括鼠标事件（如click、mouseover、mousedown等）、键盘事件（如keydown、keyup、keypress等）以及表单事件（如submit、input、change等）。这些事件为开发者提供了丰富的交互能力，可以响应用户的各种操作并相应地更新页面内容。

在事件处理过程中，浏览器还维护一个事件队列。一旦事件队列中的事件得到处理，它就会被移除。此外，浏览器还支持宏任务和微任务的概念，用于管理异步执行的任务。例如，setTimeout、setInterval等是常见的宏任务，而Promise的回调则是微任务。这些任务的执行顺序和优先级也是事件机制的一部分。

总的来说，浏览器的事件机制是一个复杂而精细的系统，它确保了用户与网页之间的交互能够正确、高效地执行。通过理解并合理利用事件机制，开发者可以创建出更加动态和响应式的网页应用。

# 垃圾回收机制

浏览器的垃圾回收机制是浏览器管理内存、确保资源有效利用的关键部分。当变量、对象或其他资源不再被使用时，垃圾回收机制会自动释放它们所占用的内存，从而防止内存泄漏。

JavaScript具有自动垃圾回收机制，会定期对不再使用的变量、对象进行清理。这主要通过两种实现方式：标记清除和引用计数。其中，标记清除是js中最常用的垃圾回收方式。当变量进入环境时，例如在一个函数中声明一个变量，这个变量会被标记为“进入环境”。而当变量离开环境时，它会被标记为“离开环境”，随后被垃圾回收机制回收。

此外，垃圾回收过程中还需要处理全局变量和局部变量。全局变量的生命周期会持续到页面卸载，而局部变量在函数执行结束后就不再被使用，它们的内存空间会被释放。但值得注意的是，当局部变量被外部函数使用时（如闭包情况），它们依然会被视为在使用中，因此不会被回收。
浏览器的垃圾回收机制虽然可以自动管理内存，但开发者仍需注意避免不必要的内存占用和潜在的内存泄漏。通过优化代码、减少全局变量的使用、及时解除不必要的引用等方式，可以有效提高应用的性能和稳定性。

总的来说，浏览器的垃圾回收机制是确保浏览器高效、稳定运行的重要机制之一。它通过自动管理内存，减少了开发者手动管理内存的复杂性，提高了开发效率。同时，开发者也需要注意合理使用内存，避免潜在的内存问题。

# 进程和线程

## 进程（Process）

进程是操作系统中资源分配的基本单位。每个进程拥有自己独立的内存空间（包括堆、栈、数据段和代码段）以及操作系统资源（如文件描述符、网络连接等）。
进程通常代表一个正在运行的程序，操作系统会为每个进程分配资源，以便它能够独立执行。
每个进程至少包含一个线程，即主线程。

## 线程（Thread）：

线程是进程中的一个执行单元，也称为轻量级进程。线程是操作系统调度的基本单位，一个进程可以包含多个线程，这些线程共享进程的内存空间和资源。
多线程可以并发执行，从而提高程序的运行效率。
在同一个进程内，线程之间可以共享数据，但也需要通过同步机制来避免数据竞争和冲突。
